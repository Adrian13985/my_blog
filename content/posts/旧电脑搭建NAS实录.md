> **公开发布版｜2026 年 10 月实践记录**
>
> 本文按实际操作记录整理，出于安全考虑已替换家庭局域网地址、公网 IPv6、个人域名、邮箱与账户信息；涉及私有路由器 SSH 的部分只讨论原理和风险，不提供固件利用步骤。示例中的 `nas.example.net`、`192.168.x.x` 均不是实际可访问地址。**“已经配置”不代表“经历了真实网络前缀变化测试”。**

## 01｜为什么折腾这台老机器

家里有一台配置并不豪华的旧主机：Intel Celeron 1037U、4 GB 内存、32 GB mSATA SSD，以及一块 500 GB 希捷机械硬盘。这个配置不适合堆大型虚拟机，也不需要为了 NAS 先买一套复杂硬件。我的目标更简单：让它成为一个全天候、能从 Windows 和手机访问、还能整合 OneDrive 的家庭文件服务器。

一开始列出的需求并不复杂：局域网通过 SMB 共享文件；网页版能浏览本地文件和云盘；出门时最好不用先连接 VPN；全部使用 HTTPS；公网 IP 变化后能自动恢复。真正困难的不是安装其中任何一个软件，而是让操作系统、文件权限、路由器、光猫、IPv6 与证书签发逻辑同时匹配。

最终采用的技术组合如下：

| 层次 | 选型 | 作用 |
|---|---|---|
| 基础系统 | Debian 13 + OpenMediaVault 8 | 磁盘、文件系统、共享与后台管理 |
| 数据盘 | 500 GB ext4 | 本地数据持久保存 |
| 局域网 | Samba / SMB | Windows 文件资源管理器直接访问 |
| 云盘 | rclone + FUSE | 将 OneDrive 以只读目录形式呈现 |
| Web 文件管理 | OpenList | 统一浏览本地文件与云端资源 |
| 保底远程通道 | Tailscale / Funnel | 作为公网直连不可用时的备用路径 |
| 公开访问 | 原生 IPv6 + Caddy | TLS 终止和 OpenList 反向代理 |
| 动态域名 | dynv6 | 自动维护公网 IPv6 的 AAAA 记录 |

这里有一个重要取舍：**不将 500 GB 机械盘误认为“安全存储”。单盘没有冗余；云盘挂载也不能代替备份。**

## 02｜硬盘：先分清系统盘和数据盘，再操作

装机后第一件应该做的事不是格式化，而是确认硬盘身份：

```bash
lsblk -o NAME,SIZE,FSTYPE,MODEL,MOUNTPOINTS
lsblk -f
sudo smartctl -a /dev/sdX
```

最初查看时，32 GB 系统盘和 500 GB 数据盘在 `/dev/sda`、`/dev/sdb` 的对应关系与后续某次启动后的盘符并不一致。数据盘原先还是 NTFS，并非直接拿来作为 OMV 的 ext4 数据卷。确认不需要保留旧数据后，才在 OMV 后台针对 **500 GB 的硬盘**清空并建立 ext4 文件系统。

这个环节最值得记住的是：**`/dev/sda`、`/dev/sdb` 不是可靠的长期身份标识。** 脚本和挂载配置应优先使用文件系统 UUID，破坏性操作必须再次核对容量、型号和序列号。

硬盘自检也踩过一个小坑：第一次运行 `smartctl -t long` 成功，再次运行时提示正在进行的自检尚未结束，剩余约 90%。这不是新故障，而是同一块盘不能同时执行两个长测。等待测试结束后，报告为 `Completed without error`。它只能说明**当次测试未报告错误**，不能替代长期监控或数据备份。

## 03｜让 Windows 真正把 NAS 当作一块网络盘

在 OMV 中创建 ext4 文件系统、挂载数据盘、建立共享文件夹，并配置 SMB/CIFS 服务。完成后，Windows 可以直接使用：

```text
\\192.168.x.x\NAS_DATA
```

也可以映射为网络驱动器。与单纯用浏览器上传下载相比，SMB 更适合管理项目文件、3D 模型、代码与常见文档。

一个容易混淆的地方是：**共享目录在 OMV 后台可见，不代表 Windows 登录账户一定有读写权限。** 应同时检查文件系统权限、共享权限和实际使用的 Samba 账户。公网不开放 SMB 的 445 端口，远程访问使用独立、安全的入口。

## 04｜将 OneDrive 挂到 NAS，而不是复制整个云盘

下一步是让云盘出现在本地目录树中。这里选择 rclone，而不是把 OneDrive 全量同步到 500 GB 硬盘。

认证时 NAS 是无图形环境，因此在 Windows 电脑上完成浏览器 OAuth 授权，再把生成的授权结果交给 NAS 的 `rclone config`。过程中的典型命令是：

```powershell
rclone authorize "onedrive"
```

认证完成后，以 `onedrive:` 作为远程名称，再通过 systemd 管理 rclone 的 FUSE 挂载。实际使用的是**只读挂载**：本地和 OpenList 可以浏览云盘，但不会因为误操作把 NAS 上的删除动作反向同步到云端。

常见错误是把“挂载”当成“备份”。挂载是一个视图：云端断网、授权失效、FUSE 进程退出都会影响目录可用性。更稳妥的方式是让挂载由 systemd 管理，开机自动启动，并在日常巡检中检查服务和挂载状态。

## 05｜OpenList：把本地目录与云端资源放进同一个网页

OpenList 的默认 Web 端口是 `5244`。本机可通过 `http://NAS内网地址:5244` 访问，并为手机端建立单独账号与相应权限。

相比让家人分别记住 SMB、OneDrive 和多个管理后台，OpenList 的优势是统一入口。但把它放到公网前，必须先完成账号隔离与权限检查，尤其不要让匿名用户获得不必要的访问权。

此时服务已经能在局域网工作，但“在家里能打开网页”与“互联网能安全访问”仍然相差好几层网络配置。

## 06｜第一条远程路径：Tailscale 先解决“能连上”

Tailscale 作为远程通道，先解决跨网络管理问题。Windows 可以通过 Tailnet IP 访问 NAS 的 SMB 共享；再通过 Funnel 将 OpenList 的本地 HTTP 服务代理为一个公开 HTTPS 地址。

它的最大价值不只是省掉端口映射，更在于给后续公网 IPv6 调试保留了一个**独立的备用入口**。当直连 DNS、证书或光猫规则出问题时，不至于完全失联。

不过，Funnel 和直连 Caddy 并不是同一个东西。它们可以共享公网 HTTPS 的使用体验，但监听地址、流量路径与故障边界不同。

## 07｜为什么有全球 IPv6 地址，却还是从外面连不进来

家里的 IPv4 是典型的上级私网/多层 NAT 场景，直接指望公网 IPv4 端口映射并不现实；所幸宽带分配了全球可路由的 IPv6 前缀。

网络拓扑可以理解为：

```text
手机 4G/5G（IPv6）
       │ HTTPS 443
       ▼
互联网 → 光猫 → 家庭路由器 WAN
                         │ IPv6 WAN→LAN 放行规则
                         ▼
                   NAS 全球 IPv6:443
                         │ Caddy
                         ▼
                   OpenList :5244
```

最初排查过程中，多次出现“NAS 确实拿到了全球 IPv6，但公网连不上”。原因最终不是 NAS 没地址，而是**光猫与家庭路由器共同构成了入站过滤链路**。路由器需只放行前往 NAS 的 IPv6 TCP 443，光猫上某项名为“防止 IPv6 Session 攻击”的功能也曾妨碍入站连接；关闭这一特定拦截选项、保留其他防护后，访问才通过。

为排除 OpenList 与证书问题，曾临时用 Python HTTP 服务绑定 NAS 的公网 IPv6 及 443 端口，然后使用手机蜂窝网络访问一个验证文件，服务端确实记录到 `GET ... 200`。**这个实验验证的是端到端入站 IPv6 通路，而不是 OpenList 认证或 HTTPS 正确性。** 测试结束后立即停止临时服务。

安全原则：只开放必要的 443，其他 WAN→LAN 规则继续拒绝。不要为了测试直接关闭整台路由器的 IPv6 防火墙。

## 08｜Caddy 与 80、443 端口的几次碰撞

NAS 上 OMV 的 nginx 已使用 TCP 80；另一方面，Tailscale 的 HTTPS 入口使用独立的 Tailnet 监听地址。若让 Caddy 随意占用所有接口的 80 或 443，就可能与现有服务冲突。

因此让 Caddy **仅绑定 NAS 的公网 IPv6 地址的 443**，并使用 ACME 的 TLS-ALPN-01 验证，不依赖 80 端口。配置思路如下（示例地址）：

```caddyfile
{
    auto_https disable_redirects
}

nas.example.net {
    bind 2001:db8:100:200::1234

    tls {
        issuer acme {
            disable_http_challenge
        }
    }

    encode gzip
    reverse_proxy 127.0.0.1:5244
}
```

曾将 `bind` 写成带方括号的 IPv6 地址，导致 Caddy 在证书挑战阶段报 `missing port in address`。在该配置项中应写**裸 IPv6 地址**，不要添加 `[...]`。此外，`curl -I` 发出的是 HTTP HEAD 请求，OpenList 返回 405 并不一定意味着网页不可用；用普通 GET 验证才对应浏览器实际访问路径。

成功签发并访问 HTTPS 后，才算完成了从移动网络到 OpenList 的端到端验证。

## 09｜DDNS 的意外：域名能用，不代表更新接口能用

开始使用的免费 DDNS 服务，其 AAAA 记录配置成功，域名也能正常解析和访问 HTTPS。但 NAS 向服务商的 HTTPS 更新接口发起请求时，TLS 握手被重置；更换客户端或解析地址后问题仍存在。令牌本身已经核对正确，因此不能简单归因于“Token 填错”。

这是一个容易遗漏的区别：

- 浏览器访问 **域名解析结果** 成功；
- NAS 连接 **DDNS 服务商 API** 成功；
- DDNS **真的可以长期自动更新**；

三件事必须分别测试。为了不在明文 HTTP 连接里泄漏 DDNS Token，最终没有采用不安全的降级方案，而是改为 NAS 能通过 HTTPS 正常访问的 dynv6 更新接口。脚本通过读取网络接口的 `/64` 全球 IPv6 与固定接口标识，必要时更新 AAAA 记录，并由 systemd 定时器约每五分钟运行一次。

结果是：新域名的 DDNS 更新已验证工作；旧域名仍可用，但其自动更新尚未解决。今后主入口优先使用新域名。

## 10｜证书限额、ZeroSSL 语法与“成功原因”

新域名所在的共享免费域名后缀，曾触发 Let's Encrypt 的“同一注册域名七天最多签发 50 张证书”限额（HTTP 429）。问题不是自己申请了 50 次，而是**共享后缀上的其他用户也可能消耗同一个限额**。

为此计划只让新域名切换到 ZeroSSL，原有域名继续使用 Let's Encrypt。这里又遇到了 Caddyfile 的语法错误：在 `tls { issuer acme { ... } }` 内写了 `ca`，校验提示 `unrecognized ACME issuer property: ca`；改为 `dir https://acme.zerossl.com/v2/DV90` 后配置通过。

但回看**带时间戳的完整日志**发现：在新 ZeroSSL 配置 reload 前，Let's Encrypt 已经解除限额并成功签发了新域名证书！这说明“切换配置后网页返回 200”**不能倒推**“证书一定由 ZeroSSL 颁发”。证书签发历史与当前续期策略要分开看。

当时新域名最终在 IPv6 HTTPS 上返回 HTTP 200；旧域名也保留了原来的入口。未来具体续期使用哪家 CA，应以 Caddy 配置、证书链和续期日志为准。

## 11｜动态 IPv6 的最后一块拼图：DNS、代理、路由器必须一起变

公网 IPv6 前缀可能改变。仅更新 AAAA 记录还不够：Caddy 的 `bind` 仍旧指向旧地址，路由器放行规则也可能仍然指向旧地址。

因此引入三个独立的自动更新环节：

| 更新对象 | 触发与职责 |
|---|---|
| dynv6 | NAS 定时检查 IPv6，更新 AAAA |
| Caddy | NAS 定时检查 IPv6，更新两处 `bind` 并验证/reload |
| 路由器防火墙 | 路由器从 LAN `/64` 前缀推导 NAS 目标地址，必要时更新 TCP 443 规则 |

路由器部分由路由器本机读取前缀，不将其管理员密码写到 NAS 的脚本里。配置与 cron 已安装，脚本在 **IP 未变化** 时通过检查；截至文稿整理时，**尚未验证一次真实的运营商 IPv6 前缀变更，也尚未收到最后一次 cron 日志确认**。这不是已经验证的“秒级无感切换”，通常也可能有数分钟的更新/缓存窗口。

## 12｜这次折腾留下的工程经验

**先做最小可验证链路。** 先让 SMB 在局域网可用，再检查 Funnel，最后拆解 IPv6 入站、DNS 和 TLS；不要把所有变量一起改。

**不要把故障表象当根因。** 端口连不上可能是光猫规则；证书失败可能是共享后缀配额；HEAD 405 可能不是网页错误；DDNS 域名正常也不意味着 API 能连通。

**让配置变化可回滚。** Caddy 更新前保留备份、执行 `caddy validate`；定时脚本在地址未变化时不写文件；路由器规则只允许目标 TCP 443。

**安全从简。** 不公开 SMB、SSH、OMV 后台；不将 DDNS Token 放进明文 URL 日志；不因调试方便而关掉路由器防火墙。

**备份优先于漂亮的仪表盘。** 一块经过 SMART 测试的老硬盘仍然可能故障。重要文件至少再有一份独立副本，最好离线或异地保存。

## 结语

旧硬件能不能做 NAS，重点不在跑分，而在于是否明确自己的需求、理解服务依赖，并且愿意把故障一层层拆开。现在这套机器能够服务本地文件、挂载云盘、提供网页管理，并通过原生 IPv6 + HTTPS 访问。最重要的收获不是某个软件的安装命令，而是把**文件系统、身份权限、反向代理、DNS、证书、路由策略和自动化运维**连接成了一条能解释、能检查、能回滚的链路。
