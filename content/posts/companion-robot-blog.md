> 用一部旧安卓手机、一块 ESP32-S3、一套自己设计的底盘，再加上家里的 NAS，把远程看画面、双向说话和小车控制接到了一起。

我想做一台可以放在异地使用的小机器人：拿起手机，就能看到它面前的画面，和现场的人说话，再控制它向前走一段、转个方向。

这个想法的核心，是让远程交流多一点“在场感”。视频通话的视角通常固定在手机支架上，而给手机加上一个能移动的底盘，视角就有了变化的可能。

我给第一版定的目标很具体：复用旧手机和已有设备，先跑通远程音视频与人工驾驶，再逐步完善整机体验。于是，这个项目从电机控制开始，一路延伸到了 PCB、结构设计、安卓 App、NAS 服务和家庭网络。

## 一、旧手机是这台机器人的音视频模块

如果从头搭一套音视频硬件，需要考虑摄像头、麦克风、扬声器、屏幕、编解码和联网。旧安卓手机已经把这些东西集成好了，还自带电池、充电管理和安装应用的能力。

所以我把系统分成了三个部分：

| 部分 | 负责什么 |
| --- | --- |
| 车载安卓手机 | 采集画面和声音，播放远端语音，运行 WebRTC |
| ESP32-S3 控制板 | 独立联网，处理驾驶指令，控制电机和失联停车 |
| 家用 NAS | 运行认证、消息转发、音视频信令和必要的媒体中继 |

遥控端也是安卓手机。两部手机安装同一个 App，分别选择车载模式和遥控模式。

这次使用的车载设备是 Redmi Note 8，系统为 Android 11；另一部手机承担遥控端。手机负责相对复杂的音视频处理，ESP32 专注于电机与本地保护，这样各部分的职责比较清楚。

最初参考过通过蓝牙把手机和底盘连起来的方案，最终实现中，ESP32 直接通过 Wi-Fi 连接 NAS。这样，电机命令不需要再经过车载手机转发，后续排查控制链路时也少了一层。

## 二、硬件和结构，要一起考虑

底盘采用两台 TT 直流减速电机、两个驱动轮和一个万向轮。主控是 ESP32-S3，电机驱动使用 DRV8833，并围绕这些器件整理了自制 PCB、接线复核和生产文件。

控制板的任务比较集中：接收方向命令，设置左右电机输出，检查驱动故障，并在通信异常时取消运动。

这一版采用固定电平控制，没有加入 PWM 调速。优先把方向、换向、停止和远程会话处理清楚，后续再增加速度控制。

供电上，我沿用了 5V 充电宝的思路。电机和主控从电源处分支供电，电机电流不经过 ESP32 的 3.3V 输出；手机保留原电池，从正常 USB 接口补电。

这里有一个很容易看错的参数：充电宝的多个接口分别标注输出能力，不代表同时使用时可以把电流直接相加。现有电源在多口模式下合计是 5V/3A，电机启动、手机充电和主控工作都要放进这个总预算里。

结构部分使用 SolidWorks 建模，并导出了 STEP 和 3MF。主底板约为 200×140mm，手机架、电机安装耳、PCB 安装柱和电源绑带槽，都围绕实际器件布置。

画结构时，麻烦经常藏在连接处：电机轴的位置影响离地间隙，USB 插头需要留出弯线空间，螺丝能穿过孔还不够，也要有拧紧的空间。电机安装耳后来根据实物改成了 M3 贯穿孔，手机架则保留了充电口开口和绑带固定位置。

原生 CAD 文件方便继续改尺寸，交换格式和打印文件方便后续制造。尺寸检查、孔位对齐和装配干涉检查也一起留了下来，便于知道模型验证到了哪一步。

## 三、NAS 让两端在外网找到彼此

服务器使用家里已有的一台低配置 NAS：Intel 1037U、2GB 内存，运行 Linux。

它承担的服务主要有四个：

| 服务 | 在项目中的作用 |
| --- | --- |
| Caddy | 提供统一 HTTPS/WSS 入口，代理网页和后端服务 |
| Mosquitto | 转发驾驶命令、设备状态和执行回执 |
| Python 信令服务 | 登录认证、两端配对、转发 WebRTC 建连信息 |
| coturn | 在媒体无法直连时提供 TURN 中继 |

音视频的采集、编解码和播放交给手机，NAS 不做视频转码，也不承担录像任务。两端能直接传输媒体时就直连，需要中继时再经过 coturn。

驾驶链路和媒体链路分别工作：

- 驾驶：遥控端通过 MQTT over WSS，把目标方向发送给 ESP32。
- 音视频：两部手机通过 WebRTC 传输，先完成认证和信令交换，再建立实际媒体连接。

这也给排错提供了方向。App 能登录，只能说明认证入口可用；有画面，只能说明媒体链路已经建立；电机是否执行，还要看设备连接和控制协议。每条链路都需要自己的验证证据。

## 四、远程驾驶里，我花了很多时间处理“停止”

小车在桌面上转起来并不难。接入外网以后，还要考虑消息迟到、页面切后台、网络重连、两个控制页面同时打开，以及旧命令会不会在恢复连接后继续执行。

因此，驾驶协议采用了持续更新目标的方式。

按住方向按钮时，客户端以约 50ms 为目标周期发送最新方向；每条有效目标只提供有限的设备运动授权，当前上限为 300ms。没有持续收到有效的新指令，ESP32 就撤销运动授权。

这个保护在设备本地执行。即使遥控端最后一条“停止”消息没能送达，设备也有自己的失联处理。

为了识别迟到和过期消息，协议还加入了启动标识、一次性准备票据、随机会话、递增序号和新鲜度校验。松开按钮会释放自己的驾驶会话，独立停止按钮则可以停止整车。

多页面操作也有细节：一个空闲页面切到后台，不应该停止另一个页面正在进行的驾驶；旧会话迟到的释放消息，也不应该打断新会话。为此，释放操作需要对应具体会话。

方向切换时，程序先关闭驱动，保留至少 100ms 的滑行间隔，再切换方向。断连、故障和重新配网都会撤销当前控制权，恢复连接以后必须重新按下按钮。

还需要说明，关闭驱动后车轮是滑行停止。300ms 是指令授权上限，100ms 是程序中的换向间隔，两者都不能直接当作机械停稳时间。实际停车距离仍取决于车速、负载、地面和机械结构。

## 五、App 把画面、语音和驾驶放在一起

原生安卓 App 提供两个模式。

车载模式使用手机摄像头、麦克风和扬声器，启动后显示本地预览与前台运行通知；遥控模式接收画面，提供方向控制、通话静音和扬声器开关。

媒体部分使用原生 WebRTC，提供 480p 和 720p 的配置入口。实际帧率、编码方式和温升，还需要结合具体手机测量，不能从界面选项直接推断。

把画面和控制放进同一个 App 后，可以让两者配合起来：遥控端需要收到新鲜画面、MQTT 状态正常，并确认固件具备相应能力后，才启用驾驶按钮。如果一段时间没有新的解码视频帧，就暂停驾驶。

这在远程控制中很有必要。画面停留在上一帧时，控制者对现场情况的判断也停留在过去，继续让车轮响应会让操作变得不可控。

车载手机仍需要现场启动 App，并完成相机、麦克风等系统授权。当前没有把手机重启后自动恢复、任意系统下熄屏长驻等能力作为已经验证的功能。

## 六、几个真正影响进展的坑

### 1. 工程换到英文路径，构建才顺利完成

在原电脑环境中，ESP-IDF/CMake 工程放在中文路径下出现过构建异常。相同源码迁移到英文路径后，构建通过。

这次排查让我更注意区分源码问题和环境问题：如果代码没有变化，先检查路径、工具链和构建目录，也能缩小范围。最后把当前有效工程和历史副本明确区分开，避免修改一份、烧录另一份。

### 2. 网页能打开，控制资源也可能没部署完整

网页控制端曾出现旧界面和组件加载失败的问题。检查后补齐了本地 MQTT JavaScript 依赖，也修正了从本地文件或 localhost 打开时的后备连接地址。

后来还增加了独立版本入口、带版本号的脚本文件和禁缓存响应头。这样，看到“网页能打开”以后，还能继续确认：页面版本对不对，脚本是不是这一版，连接地址是不是预期的服务器。

### 3. Wi-Fi 切到 5G，暴露了重连线程问题

App 在切换网络时出现过闪退。实际崩溃栈指向 WebSocket 的重连调用：匿名回调中的同名方法解析到了库的同步重连方法，而它不适合在当时的回调线程里执行。

修复时，把重连调度明确指向自己的逻辑，通过独立定时器重试，并处理结束连接时的并发情况。随后用真实库回调做主机回归，再进行手机切网复测。

这个问题提醒我，重连流程需要单独设计，不能只在失败回调里再调用一次连接函数。

### 4. HTTPS 正常，5G 仍然没有声画

这是网络部分最有代表性的一次排查。

当时网页登录和信令连接都正常，同 Wi-Fi 下的音视频也已跑通，但换到移动网络后仍然连接失败。进一步检查发现，路由器只放行了 NAS 的 HTTPS 入口，TURN 需要的入口和媒体中继端口没有完整放行。

补上针对 NAS 的精确规则后，5G 下的画面和双向声音恢复，App 也显示实际使用了中继。

因此，HTTPS、信令连接、TURN 入口和媒体中继端口，需要分开检查。最终验收也要回到真实 App：实际选路是否符合预期，画面是否持续更新，双方是否都能听到声音。

## 七、这一版做到了什么

目前已经把硬件、结构、控制协议、安卓 App 和 NAS 服务串成了一套原型，并保留了源码、设计文件和部署记录。

验证结果需要分层来看：

| 项目 | 已有结果 |
| --- | --- |
| 同 Wi-Fi 音视频 | 两端直连，画面和双向声音已确认正常 |
| 车载 Wi-Fi、遥控 5G | 实际媒体中继下的画面和双向声音已确认正常 |
| 网页与固件控制逻辑 | 会话、过期、松手、断连和故障等主机测试通过 |
| 安卓切网重连 | 已完成问题修复，并进行了手机复测 |
| CAD | 已进行尺寸、孔位和当前装配模型的干涉检查 |

此外，停车距离、持续驾驶电流、温升、长时间稳定性，以及最初设想的 4～5 小时续航，还需要整机测试。

App 显示的网络往返时间也只描述相应链路的 RTT。摄像头采集、编码、传输、解码和显示都会影响最终画面延迟，不能用一个网络读数概括整套体验。

这也是我整理项目记录时很在意的一点：代码实现、模拟测试、实机反馈和长期验证，分别说明各自能证明的事情。

## 八、这次项目给我的收获

这个项目把几种原本分开的学习内容接到了一起：嵌入式决定电机何时动作，机械结构决定器件怎么装，安卓决定怎样使用手机的音视频能力，服务器和家庭网络决定它们能否在异地连通。

越往后做，越能感受到接口的重要性。底板和电机之间有安装接口，App 和固件之间有协议接口，NAS 和路由器之间也有网络边界。很多问题恰好出现在这些连接处。

旧手机的复用，让我可以把有限精力放在系统整合上；ESP32 的本地保护，让驾驶控制有了独立于手机和公网的停止逻辑；已有 NAS 则给了整个原型一个持续运行的服务端。

下一步，我更想把现有体验测清楚、磨稳定：确认真实续航，记录停车距离与温升，量化画面延迟，再考虑调速、状态监测等改进。

这台小车承载的想法很朴素：让远程交流多一个能够移动的视角。把这个想法做成一套能连接、能观察、能控制，也能在连接丢失后停止的系统，就是这次项目最有意思的地方。
